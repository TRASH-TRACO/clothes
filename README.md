# CLOSET

내가 가진 옷을 **사진 · 실측 · 색상**으로 기록하고, 모자/아우터/상의/하의/신발/액세서리를 한 화면에서 조합해 **코디를 저장**하는 앱.

- **Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4**
- **Supabase** (Postgres + Auth + Storage)
- **Vercel** 배포 전제
- 디자인은 나이키 페이지 톤 — 흰 바탕, 굵은 대문자 헤드라인, 정사각 이미지 그리드, 검은 필 버튼

## 왜 Supabase인가

| | Supabase | Firebase |
|---|---|---|
| 옷 ↔ 코디 다대다 | 조인 테이블 하나로 끝 | 문서 비정규화 필요 |
| 실측/색상 필터링 | SQL(`where`, `jsonb`)로 바로 | 복합 인덱스 수동 관리 |
| 사진 | Storage 공개 URL → `next/image` | Storage + 토큰 URL |
| 사용자 격리 | RLS 정책으로 선언적 | 보안 규칙 DSL |

실시간 동기화가 핵심이 아닌 앱이라 관계형 쪽이 유리해서 Supabase로 갔습니다.
데이터 접근은 `lib/data.ts`와 `app/actions/*`에 모여 있어 다른 백엔드로 바꿔도 화면 코드는 그대로입니다.

## 시작하기

### 1. Supabase 프로젝트 만들기

1. [supabase.com](https://supabase.com)에서 새 프로젝트 생성
2. **SQL Editor**에 [`supabase/schema.sql`](supabase/schema.sql) 전체를 붙여넣고 실행
   - 테이블(`items`, `outfits`, `outfit_items`), RLS 정책, `clothes` Storage 버킷이 한 번에 만들어집니다
   - Storage 정책 생성에서 권한 오류가 나면 대시보드 **Storage → clothes → Policies**에서 같은 규칙을 UI로 추가하세요
3. **Authentication → Providers → Email**에서 이메일 로그인이 켜져 있는지 확인
   - 혼자 쓸 거라면 **Confirm email**을 꺼두면 가입 즉시 로그인됩니다

### 2. 환경변수

```bash
cp .env.example .env.local
```

`Project Settings → API`에서 값을 복사해 채웁니다.

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...

# AI 코디 추천용. 회원이 맡긴 키를 잠글 때 씁니다 (없으면 키를 안 받습니다).
#   openssl rand -base64 32
APP_SECRET=...

# (선택) 서버 공용 키. 회원이 자기 키를 안 넣었을 때만 씁니다.
ANTHROPIC_API_KEY=sk-ant-...
```

### 3. 실행

```bash
npm install
npm run dev
```

http://localhost:3000 → 회원가입 → 옷 등록.

### 4. Vercel 배포

1. GitHub 저장소를 Vercel에 Import (프레임워크 자동 감지)
2. **Environment Variables**에 위 값을 등록 (`APP_SECRET`은 AI 추천을 쓸 때만)
3. Deploy

`next.config.ts`가 `NEXT_PUBLIC_SUPABASE_URL` 호스트를 이미지 도메인으로 자동 등록하므로 별도 설정이 필요 없습니다.

### 5. 홈 화면에 설치 (PWA)

배포한 주소를 폰에서 열면 주소창 없는 앱처럼 쓸 수 있습니다. **HTTPS에서만** 동작하므로
`localhost`가 아니라 Vercel 주소로 접속해야 합니다.

> iOS는 `apple-mobile-web-app-status-bar-style`을 **홈 화면에 추가한 시점에 저장**합니다.
> 값을 바꿔도 이미 깔린 아이콘에는 반영되지 않으므로, 메타만 믿지 않고 상태바가 화면을
> 덮는지 직접 잽니다. `app/layout.tsx`의 인라인 스크립트가 `navigator.standalone`이면서
> `innerHeight >= screen.height`이면 `<html>`에 `data-status-overlay`를 답니다.
> 덮을 때만 헤더 맨 위 `.status-band`가 검은 띠로 그 자리를 메웁니다 (`app/globals.css`).
> 전체화면에서 `env(safe-area-inset-top)`이 0으로 오는 경우가 있어 최소 높이를 함께 둡니다.

- **iOS (사파리)**: 공유 버튼 → **홈 화면에 추가**
- **안드로이드 (크롬)**: 주소창 메뉴 → **앱 설치** (조건이 맞으면 설치 배너가 뜹니다)

설치하면 주소창 없는 전체화면으로 뜨고, 안드로이드에서는 아이콘을 길게 눌러
`옷 등록 / 코디 만들기 / 옷장` 바로가기를 쓸 수 있습니다.

| 파일 | 하는 일 |
|---|---|
| `app/manifest.ts` | 이름·아이콘·시작 URL·바로가기 (`/manifest.webmanifest`로 나감) |
| `app/layout.tsx` | `viewport`(테마색·`viewport-fit=cover`)와 애플 전용 메타 |
| 상태바 | 덮는지 재서 `data-status-overlay`를 달고, 그때만 헤더 맨 위 `.status-band`가 검게 메웁니다 |
| `app/apple-icon.png` | iOS 홈 화면 아이콘 180px |
| `public/icon-*.png` | 매니페스트 아이콘 192·512, 안드로이드용 maskable 512 |

아이콘은 헤드라인 폰트(Anton)의 `C`를 잉크색 바탕에 얹은 레터마크입니다.
maskable 쪽은 안드로이드가 원형으로 잘라내는 걸 감안해 글자를 더 작게 넣었습니다.

### 새로고침

전체화면으로 띄우면 주소창이 없어 새로고침할 방법이 마땅치 않습니다 (`components/app-refresh.tsx`).

- **앱으로 돌아오면 알아서 최신으로 맞춥니다.** 다른 앱에 갔다 오거나 화면을 다시 켜면
  서버 컴포넌트만 다시 받아옵니다 (`router.refresh()` — 전체 새로고침이 아니라 화면이 깜빡이지 않습니다).
  너무 잦지 않게 30초 안에 다시 돌아오면 건너뜁니다.
- **헤더에 새로고침 버튼**이 생깁니다. 전체화면으로 실행 중일 때만 보입니다 —
  브라우저로 열었다면 주소창의 새로고침이 이미 있으니까요.

**오프라인은 아직 안 됩니다.** 모든 화면이 로그인 사용자 데이터라 `force-dynamic`이고,
서비스 워커를 두지 않았습니다. 설치와 전체화면 실행에는 서비스 워커가 필요 없습니다.

## 날씨

옷은 날씨를 따라가므로 홈 맨 위에 기온·강수량을 띄웁니다.

- **오전에는 오늘, 오후 5시(KST)부터는 내일 예보**를 봅니다. 저녁엔 내일 뭘 입을지 고민하니까요.
- 위치는 홈 헤드라인(`오늘 뭐 입지 고민 끝`) 옆입니다. 스크롤 없이 바로 보이라고 로그인한 사람의
  히어로에서는 소개 문구를 빼고 여백을 줄였습니다 (`components/home-hero.tsx`).
- 보여주는 값: 기온(오늘은 현재, 내일은 예상 최고), 최고/최저, 체감, 강수확률, 강수량, 최대 풍속,
  그리고 06·09·12·15·18·21시 기온 (오늘 예보에서 이미 지난 시간은 흐리게).
- 기온 밑에 **전날과 비교한 한 줄**이 붙습니다 — `어제보다 6° 추워요`, `오늘과 비슷해요 · 바람도 많이 불어요`.
  오늘 예보면 어제와, 내일 예보면 오늘과 비교합니다 (내일 옷은 오늘 입은 것과 견주는 게 자연스러워서).
  최고기온 차가 2° 미만이면 "비슷해요", 그 이상이면 몇 도 차이인지 말합니다. 바람이 전날보다
  3m/s 이상 세지면서 6m/s를 넘거나, 일교차가 12°를 넘으면 한마디가 더 붙습니다 (`compareLine()`).
- [Open-Meteo](https://open-meteo.com)를 쓰기 때문에 **API 키가 필요 없습니다.** 응답은 30분 캐시합니다.
- **한 번 본 날은 DB에 저장합니다** (`daily_weather`). 어느 지역 기준이었는지도 같이 남깁니다.
  그 뒤로는 DB에서 읽으므로 같은 날을 다시 부르지 않고, 예보 API가 주는 기간(과거 92일)이
  지나도 기록이 남습니다. 오늘과 그 이후는 예보라 3시간마다 다시 받아 덮어씁니다.
- 날씨를 못 불러와도 홈은 그대로 뜹니다 (`getWeather()`가 `null`을 주면 그 영역만 사라집니다).

### 지역은 사용자가 정합니다

**접속 위치로 추측하지 않습니다.** 날씨는 그날의 기록이라 추측값이 남으면 곤란합니다 —
여행지에서 앱을 열었다고 지난 기록의 날씨가 그 지역으로 바뀌면 기록이 아니게 됩니다.

1. `/settings` 에서 정한 **기본 지역** (`user_settings` 테이블)
2. 아직 안 정했으면 `WEATHER_LAT` / `WEATHER_LON` 환경변수 (`WEATHER_CITY`로 표시 이름)
3. 그것도 없으면 서울

하루만 다른 지역이었다면 캘린더에서 그 날짜에 지역을 적어둡니다. 그 날은 홈·캘린더 모두
그 지역 기준으로 보여줍니다.

지역 검색은 [Open-Meteo 지오코딩](https://open-meteo.com/en/docs/geocoding-api)이라 키가 필요 없고
해외 도시도 나옵니다 (`app/actions/places.ts`). 검색이 안 되더라도 자주 쓰는 국내 도시는
`lib/places.ts`의 `QUICK_PLACES`에서 바로 고를 수 있습니다. 브라우저 위치 권한은 쓰지 않습니다.

## 캘린더

달력에서 하루하루가 어떤 날씨였고 뭘 입었는지 봅니다.

- **기본으로 채워지는 값**: 최고/최저 기온, 강수량. 비가 온(올) 날은 날짜 옆에 파란 물방울이 붙습니다
  (`--color-rain`. 주황 `accent`는 경고처럼 보여서 비에는 안 씁니다).
- **직접 남기는 값**: 그날 입은 옷과 **있던 지역**. 저장한 코디를 고르면 그 구성 옷이 그대로
  채워지고, 거기서 하나씩 빼거나 더할 수 있습니다. 메모도 남길 수 있습니다.
- 지역은 여행처럼 기본 지역과 달랐던 날만 적으면 됩니다. 옷을 안 골라도 지역만 남길 수 있습니다
  ("이 날은 부산에 있었다"). 여행 가기 전에 미리 적어둬도 됩니다.
- **그날 체감**(🥶 추웠다 / 😊 적당했다 / 🥵 더웠다)을 골라둘 수 있습니다.
  달력에도 표시되는데, 좁은 화면에서는 자리가 없어 **색 점으로만** 보이고 태블릿부터 이모지가 나옵니다. 기온만으로는 안 남는 것이라,
  다음에 비슷한 날씨일 때 참고가 됩니다. 안 고르면 비워둡니다 (고른 걸 다시 누르면 풀립니다).
- 달력 칸에는 그날 입은 옷을 **최대 4장까지 2×2로** 보여줍니다 (착장 사진이 있으면 그게 우선).
- 날짜를 누르면 **달력 위에 패널로 열립니다.** 서버를 부르지 않습니다 — 달력이 이미 그 달의
  기록과 날씨를 들고 있고, 옷·코디 목록은 레이아웃에 있기 때문입니다.
  남긴 게 있는 날은 보기 화면이, 없는 날은 바로 입력 화면이 뜹니다.
- 열린 날짜는 주소(`?d=`)에 담깁니다. 링크를 복사해 바로 그 날짜를 열 수 있고, 뒤로 가기로
  닫힙니다. 주소는 `history.pushState`로만 바꾸므로 이때도 서버를 부르지 않습니다.
### 날씨는 이렇게 채워집니다

**모든 날짜를 `daily_weather`에 저장합니다.** 지역을 따로 정한 날만 저장하던 때가 있었는데,
그러면 나머지 날은 볼 때마다 **그 시점의** 기본 지역으로 다시 받게 됩니다. 설정에서 기본 지역을
바꾸면 이미 기록해 둔 지난 날의 날씨까지 딸려 바뀌었습니다. 지난 날씨는 예보가 아니라 기록이라
그러면 안 됩니다.

다시 받을지 정하는 규칙은 `lib/weather-freshness.ts` 한 곳에 모아 뒀습니다.
핵심은 **지역이 굳는 시점**입니다.

1. 저장된 게 없으면 받는다.
2. **지난 날과 기록을 남긴 날은 지역이 굳는다.** 설정에서 기본 지역을 바꿔도 따라가지 않습니다.
   아직 안 지난 날이어도 그날 뭘 입었는지 적었으면 굳습니다 — 그게 기록이니까요.
   예외는 그날 지역을 **직접 고쳐 적은** 경우뿐입니다 (`그날 나는 부산에 있었다`).
3. **값**은 다릅니다. 지난 날은 확정이라 그대로 두지만, 오늘과 앞으로는 예보라
   같은 지역이어도 받아둔 지 3시간이 넘으면 다시 받습니다.

기록을 저장하는 순간 그 날 날씨도 같이 굳힙니다 (`freezeDay()`). 달력을 열 때도 저장하지만,
저장을 누른 자리에서 굳혀 두면 달력을 안 열고 설정부터 바꿔도 기록이 흔들리지 않습니다.

화면에는 **그때 적어 둔 지역**을 보여줍니다 (`RecordedDay`). 기록은 그때 지역으로 굳으므로
나중에 기본 지역을 바꾸면 지금 기본 지역과 달라지는데, 현재 값을 그대로 붙이면 거짓말이 됩니다.
그래서 날짜 화면은 지금 기본 지역과 같으면 `서울 (기본)`, 다르면 `서울 (기록)`으로 적습니다.

> `daily_weather` 저장이 실패하면 날씨가 기록으로 굳지 않고 볼 때마다 **지금** 기본 지역으로
> 다시 받습니다. 화면은 멀쩡히 뜨기 때문에 알아채기 어려워서, 읽기·쓰기 실패는
> `[weather] daily_weather ...` 로 서버 로그에 남기고 **`/settings` 아래쪽에 상태를 띄웁니다**
> (`weatherStoreStatus()`). 며칠치가 저장돼 있는지, 안 되면 왜 안 되는지 보여줍니다.
> 지역을 바꿨는데 지난 날씨가 따라 바뀐다면 거기부터 보세요 — 대개 마이그레이션을 안 돌려
> 테이블이 없는 경우입니다.

규칙만 따로 확인할 수 있습니다 (네트워크도 DB도 필요 없습니다):

```bash
npm run check
```

여행 가기 전에 미리 그 날짜의 지역을 정해 둘 수 있습니다. 아직 안 지난 날이므로 예보가
그 지역으로 바뀌고, 날이 지나면 그대로 기록으로 굳습니다.

지역 지정을 지우면 기본 지역 값으로 되돌립니다 — 사용자가 직접 고친 것이므로 지난 날이어도
다시 받습니다. 지역을 애초에 안 적었던 날은 건드리지 않습니다. 과거 92일보다 옛날이거나
15일보다 먼 미래는 API가 주지 못하므로 아예 부르지 않습니다. 그전에 저장해 둔 날은 그대로 남습니다.
- 하루에 한 줄입니다 (`user_id + worn_on` 유니크). 같은 날짜에 다시 저장하면 덮어씁니다.
- 코디를 골라 저장해도 **구성 옷을 복사해 둡니다.** 나중에 그 코디를 고치거나 지워도
  지난 기록은 그대로 남습니다.
- 날씨는 [Open-Meteo](https://open-meteo.com) 예보 API가 주는 **과거 92일 ~ 이후 15일** 구간만
  채워집니다. 그 밖의 달을 보면 날씨 칸만 비고 기록은 정상적으로 보입니다.

> **이미 배포한 프로젝트라면 `supabase/schema.sql`을 SQL Editor에서 다시 실행하세요.**
> `wear_logs` / `wear_log_items` / `user_settings` / `daily_weather` 테이블과 RLS 정책,
> 그리고 `wear_logs`의 지역 칼럼(`place_name`, `place_lat`, `place_lon`),
> 한 줄 평가 칼럼(`wear_logs.felt`, `outfits.rating`), 세분류 칼럼(`items.subcategory`)이
> 새로 추가됐습니다.
> 여러 번 실행해도 안전합니다. 실행 전에는 캘린더가 날씨만 보여주고 기록은 저장되지 않습니다.

## 옷 등록은 한 번에 하나씩

`components/item-form.tsx` 하나가 등록과 수정을 다 합니다. 다만 태도가 다릅니다.

- **등록**은 다섯 단계로 묻습니다: 사진 → 어떤 옷 → 무슨 색 → 이름 → 마무리.
  처음 쓰는 사람이 무엇을 채워야 할지 고민할 게 없고, 폰에서 긴 폼을 훑어 내리지 않아도 됩니다.
- **수정**은 한 곳만 고치러 들어오므로 단계를 밟지 않고 모든 칸을 한 화면에 폅니다
  (`editing` 이면 진행바도 없고 실측도 펼친 채로 둡니다).
- 모든 칸은 **항상 DOM 에 있고** 안 보이는 단계만 `hidden` 클래스로 감춥니다.
  `display: none` 인 input 도 폼에 실리므로, 마지막 단계에서 한 번에 제출됩니다.
  그래서 서버 액션(`app/actions/items.ts`)은 손대지 않았습니다.
- `required` 는 쓰지 않습니다. 안 보이는 칸에 걸리면 브라우저가 "포커스할 수 없다"며 멈춥니다.
  대신 단계마다 다음 버튼을 잠그고, 마지막 방어선은 서버 액션이 봅니다.
- **이름을 대신 지어 줍니다.** 색을 고르면 `색 + 세분류`로 이름을 채웁니다 (네이비 반팔 티셔츠).
  지우고 다시 쓸 수 있고, 이미 적어 둔 이름은 건드리지 않습니다.
- 세분류·색을 고르면 180ms 뒤 다음 단계로 넘어갑니다. 곧바로 넘기면 눌렀는지 모릅니다.
- 실측·메모는 접어 둡니다. 대부분 안 적는 값이라 마지막 화면을 길게 만들 이유가 없습니다.
- **입력 칸 글자는 16px 아래로 쓰지 않습니다.** iOS는 그보다 작은 칸에 커서가 들어가면
  화면을 확대해 버리고, 확대된 채로 남아서 다음 칸을 누르기 어려워집니다. viewport에
  `maximum-scale=1`을 박아도 막히지만 손가락으로 옷 사진을 키워 볼 수 없게 되므로,
  확대할 이유 자체를 없앴습니다 (`app/globals.css`의 `input, select, textarea` 규칙).

## 사이즈감

표기 사이즈(M, 100)와 실제로 입어본 느낌은 다릅니다. 옷마다 따로 적어둡니다.

**작다 · 레귤러 · 오버핏 · 크다** 네 단계입니다. 왼쪽에서 오른쪽으로 갈수록 품이 넉넉해지는
순서라 줄 자체가 눈금 노릇을 합니다. 가운데 둘은 입을 만한 것이고, 양끝은 안 맞는 것입니다.

- 안 적어도 됩니다. 고른 걸 다시 누르면 풀립니다.
- 체감·만족도와 달리 **아이콘을 안 씁니다.** 네 개 중 둘("레귤러"·"오버핏")은 그릴 그림이
  마땅치 않고, 글자가 곧 설명이라 그림이 필요 없습니다.
- 보이는 곳: 등록·수정 폼, 옷 상세(사이즈 줄), 옷장 카드, **실측 비교**.
- **실측 비교에서 숫자 옆에 같이 뜹니다.** "어깨 52cm"라는 숫자와 "입어보니 오버핏"이라는
  몸으로 느낀 감각이 한 자리에서 만나야 살지 말지 정할 수 있습니다.
- **AI 추천에도 실립니다.** 품이 `작다`고 적힌 옷은 되도록 피하라고 일러둡니다 —
  안 맞아서 안 입는 옷이니까요.

> 원래는 "어디가 큰지"(어깨/기장/소매)까지 받으려 했습니다. 실측 항목이 곧 부위라 목록을
> 그대로 쓸 수 있는데, 일단 한 축으로 두고 써보기로 했습니다. 나중에 붙일 자리는 남아 있습니다.

## 실측 비교

`/compare`. 옷 두 벌을 골라 실측을 나란히 놓고 **차이(cm)** 를 보여줍니다.
"이 반팔이 가지고 있는 것보다 기장이 4cm 기네" 를 보고 살지 말지 정하려는 기능입니다.
옷 상세의 `다른 옷과 비교 →` 로 들어가면 그 옷이 왼쪽에 꽂힙니다 (`/compare?a=<id>`).

- **한쪽에라도 적혀 있는 항목은 모두 보여줍니다.** 한쪽만 있으면 차이는 못 내지만
  "저건 안 재어 놨다"는 것 자체가 정보입니다 (`―` 로 표시).
- 분류가 달라도 견줄 수 있습니다. 같은 `key` 만 차이가 나오고 나머지는 `―` 입니다.
  이름표가 분류마다 다른 `key`(상의 `length`=총장, 액세서리 `length`=길이)는 **왼쪽 옷을 따릅니다.**
- 큰 쪽 숫자를 진하게 해서 표만 훑어도 어느 게 큰지 보이게 했습니다.
- 고른 옷은 주소에 남깁니다 (`replaceState`, 서버는 안 부릅니다). 링크를 그대로 열면 같은 비교가 뜹니다.
- 폰에서 **`차이` 칸이 잘리지 않게** `table-fixed` 로 폭을 나누고 옷 이름은 줄여서 보여줍니다.
  그게 보려고 들어온 값이라 가로 스크롤 뒤에 숨으면 안 됩니다.

계산 규칙은 `lib/compare.ts` 에 따로 뒀고 `npm run check` 로 확인합니다 (12가지).

## AI 코디 추천

`/recommend`. 옷장과 오늘 날씨, 최근에 입은 기록을 같이 보고 **가지고 있는 옷으로** 조합을
2~3개 골라 줍니다. 마음에 들면 `이 조합으로 코디 만들기`로 코디 만들기 화면에 그대로 실려 갑니다
(`/studio?top=<id>&bottom=<id>` — 원래 있던 기능입니다).

| 파일 | 하는 일 |
|---|---|
| `lib/claude.ts` | 클라이언트와 모델 이름. 회원 키 → 서버 키 순으로 고릅니다 |
| `lib/secret.ts` | 맡긴 키를 잠그고 푸는 부분 (AES-256-GCM) |
| `app/actions/ai-key.ts` | 키 저장·삭제. 저장 전에 한 번 써 봅니다 |
| `components/ai-key-form.tsx` | 설정 화면의 키 칸 |
| `lib/recommend-prompt.ts` | 무엇을 보낼지 만드는 부분. **아무 모듈도 안 뭅니다** |
| `app/actions/recommend.ts` | 서버 액션. 부르고, 돌아온 답을 옷장과 대조 |
| `components/recommend-panel.tsx` | 화면 |
| `bin/check-recommend-prompt.ts` | 보내는 내용 확인 (`npm run check`) |

### 키는 회원이 각자 맡깁니다

`/settings` 에서 자기 Anthropic 키를 넣습니다. **요금도 각자 냅니다.** 한 사람이 많이 써서
다른 사람이 막히는 일이 없고, 서버 주인이 남의 사용료를 대신 내지도 않습니다.
서버 공용 키(`ANTHROPIC_API_KEY`)는 회원이 자기 키를 안 넣었을 때만 쓰는 대비책입니다
(혼자 쓰거나 시험할 때).

- 키는 `user_settings.anthropic_key_cipher` 에 **서버의 `APP_SECRET` 으로 잠가서** 넣습니다
  (AES-256-GCM, `lib/secret.ts`). DB만 새어 나가도 키가 그대로 털리면 안 됩니다.
  둘 다 새면 소용없지만, 한쪽만 새는 사고가 훨씬 흔합니다.
- **평문은 브라우저로 안 보냅니다.** 화면에는 꼬리 네 자리만 남긴 `sk-ant-…ab12` 가 뜹니다.
  저장한 키를 다시 보여줄 이유가 없고, 안 보내면 새어 나갈 자리도 줄어듭니다.
- **저장 전에 한 번 써 봅니다** (`models.list`, 토큰을 쓰지 않아 공짜입니다). 오타 난 키를
  그대로 넣어두면 나중에 추천을 누를 때가 돼서야 실패하고 원인도 알기 어렵습니다.
- `APP_SECRET` 이 없으면 키를 **아예 안 받습니다.** 잠글 수 없는데 받으면 평문으로 두게 됩니다.
- `APP_SECRET` 을 바꾸면 이미 맡아둔 키를 못 풉니다. 그때는 없는 것처럼 굴고, 다시 등록하면 됩니다.
- 키는 로그에 남기지 않습니다 (확인이 실패해도 예외 메시지만 남깁니다).

규칙은 확인할 수 있습니다 (`npm run check`): 잠갔다 풀면 원래 값인지, 같은 값도 매번 다른
암호문이 되는지, 다른 `APP_SECRET`이나 망가진 값으로는 못 푸는지.

### 그 밖에

- **모델은 `claude-opus-5`**, 적응형 사고에 `effort: "low"`입니다. 옷 몇십 벌 중에 고르는 일이라
  깊게 생각할 필요가 없고, 사람이 기다리는 시간도 짧아야 합니다.
- **결과는 구조화 출력**으로 받습니다 (`output_config.format` + zod). 모델이 문장으로 답하면
  파싱이 깨지는데, 스키마를 주면 `{ name, itemIds, reason }` 모양이 보장됩니다.
- **돌아온 id 는 전부 옷장과 대조합니다.** 없는 옷을 지어내면 버리고, 한 분류에 두 벌이 오면
  앞의 것만 남깁니다. 남은 게 두 벌 미만이면 그 조합은 버립니다. 모델을 믿고 그리지 않습니다.
- 지시문은 시스템 프롬프트에 두고 `cache_control`을 겁니다. 매번 바뀌는 건 옷 목록·날씨뿐이라
  앞부분이 그대로 캐시에 남습니다.
- 키가 없으면 그 화면에 안내와 설정 링크만 띄웁니다. 나머지 기능은 아무 영향 없습니다.
- `maxDuration = 60` — 모델이 생각하는 동안 기다려야 해서 Vercel 기본 제한으로는 모자랍니다.

보내는 내용은 네트워크 없이 확인할 수 있습니다:

```bash
npm run check
```

## 사진은 올리기 전에 브라우저에서 굽습니다

`lib/image.ts`가 자르기·축소·JPEG 변환을 다 하고, 결과만 Storage로 바로 올립니다
(서버 액션 본문으로 큰 파일이 오가지 않습니다).

- 긴 변이 1600px을 넘으면 줄입니다. 요즘 폰 사진은 한 장에 5MB씩 나갑니다.
- 비율을 맞추다 여백이 생기면 원본을 흐리게 깔아 채웁니다.
- **투명한 자리는 옷 색에서 뽑은 바탕색으로 깔고 굽습니다** (`readBackdrop()`).
  JPEG에는 투명이 없어서, 누끼 딴 PNG를 그냥 변환하면 투명했던 자리가 **검정**이 됩니다
  (캔버스는 아무것도 안 그리면 투명이고, 투명은 JPEG에서 검정으로 떨어집니다).
  검은 신발 누끼를 올렸더니 신발과 배경이 붙어 아예 안 보이는 일이 있었습니다.

  상품 사진 미리보기가 하는 것과 같은 방식입니다. 축소본에서 불투명한 픽셀만 모아 평균색을
  내고, **색상은 그대로 두되 채도를 1/3로 낮춰서** 깝니다. 진하게 깔면 옷보다 배경이 먼저
  보입니다.

  | 옷 | 바탕 |
  |---|---|
  | 무채색 (검정·회색) | `#f5f5f5` — 카드 바탕과 같은 값이라 사진 경계가 안 보입니다 |
  | 빨강 | `rgb(245,239,239)` |
  | 네이비·데님 | `rgb(241,242,244)` |
  | 흰색처럼 밝은 옷 | `rgb(230,230,230)` — 바탕을 낮추지 않으면 옷이 묻힙니다 |

  그림자처럼 반투명한 가장자리는 색 통계에서 뺍니다 (섞이면 탁해집니다). 빈 자리가 5% 미만이면
  누끼가 아니라고 보고 기본색을 씁니다. 누끼 사진에는 여백용 블러 배경도 깔지 않습니다 —
  물체의 흐릿한 그림자가 생기기 때문입니다. 불투명한 사진은 어차피 위에 덮이므로 달라지지 않습니다.

## 홈 헤드라인 뒤 배경

`오늘은 / 뭐 입어볼까요?` 뒤에 옷장 사진을 깝니다. 화면 폭에 따라 그림이 다릅니다.

### 넓은 화면 — 옷 물결 (`components/closet-wave.tsx`)

- 사인 곡선을 따라 22자리를 잡고, 각 자리를 곡선에서 얼마나 벗어났는지에 따라
  크기와 진하기를 정합니다. 줄기에 가까울수록 크고 진해서 은하수처럼 보입니다.
- 뽑기는 **날짜를 시드로 쓰는 고정 난수**입니다. 새로고침해도 배치가 튀지 않고 날이 바뀌면
  다른 옷이 뜹니다. (렌더 중 `Math.random()`은 `react-hooks/purity` 규칙에도 걸립니다.)
- **사진이 있는 옷만** 씁니다. 3장 미만이면 아무것도 그리지 않습니다.
- 사진은 원본을 그대로 받으므로 서로 다른 사진은 최대 10장까지만 쓰고 나머지 자리는 돌려 씁니다.
  더 촘촘하게 하려면 `COUNT`를, 사진을 더 다양하게 하려면 `MAX_PHOTOS`를 올리면 됩니다.
- **천천히 일렁입니다.** 한 주기 12초짜리 CSS 애니메이션이고, 오른쪽으로 갈수록 시작 시점을
  늦춰 파도가 지나가는 것처럼 보입니다. 줄기에 가까운(큰) 사진이 더 크게 움직입니다.
  자바스크립트 없이 `transform`만 바꾸므로 메인 스레드를 쓰지 않습니다.
- 운영체제에서 **움직임 줄이기**를 켜둔 사람에게는 멈춰 있습니다 (`prefers-reduced-motion`).

### 좁은 화면 — 옷걸이 (`components/closet-rail.tsx`)

물결은 가로로 긴 그림이라 폰에서는 헤드라인과 겹쳐 지저분했습니다. 대신 옷장 봉에 옷을 겁니다.

- 봉을 따라 9벌을 고르게 걸고, 고리 길이·크기·흔들리는 속도를 제각각으로 줘서
  한 줄로 늘어선 티가 안 나게 합니다. 짧게 걸린 옷이 진자처럼 더 빨리 흔들립니다.
- 흔들림 축은 `transform-origin: top center` — 봉에 걸린 지점입니다.
- 아래로 갈수록 흐려집니다 (`.rail-fade`의 `mask-image`). 그래서 헤드라인과 날씨 카드를
  건드리지 않습니다. 히어로 한가운데에 두면 날씨 카드가 배경을 거의 다 덮습니다.
- 뽑기 규칙과 `prefers-reduced-motion`은 물결과 같습니다. 고정 난수는 `lib/seeded.ts`에서
  둘이 같이 씁니다.
- 장식이라 `aria-hidden` + `pointer-events-none` 이고, 좁은 화면에서는 절반만 띄우고
  크기도 `--wave` 로 함께 줄입니다.

## 한 줄 평가

기록해두고 다시 안 보면 의미가 없어서, 고르는 데 1초 걸리는 것만 남깁니다.

| 어디 | 무엇 | 값 |
|---|---|---|
| 캘린더의 하루 | 그날 체감 | `cold` 추웠다 · `ok` 적당했다 · `hot` 더웠다 |
| 코디 | 입어보니 어땠나 | `bad` 별로였다 · `ok` 적당했다 · `good` 맘에 들었다 |

- 체감은 이모지(🥶 😊 🥵), 만족도는 흑백 선 아이콘(찡그림 · 무표정 · 웃음)으로 고릅니다.
- **고르지 않아도 됩니다.** 고른 걸 다시 누르면 선택이 풀립니다.
- 값은 `lib/feedback.ts`에 모여 있고, DB에서도 `check` 제약으로 세 값만 받습니다.
- 코디 만족도는 저장한 코디 목록·상세에, 그날 체감은 날짜 보기 화면에 표시됩니다.

## 화면 전환

탭을 눌렀는데 아무 반응이 없으면 사용자는 한 번 더 누릅니다. 세 겹으로 막습니다.

1. **누른 즉시 반응** — Tailwind 기본값이 모바일 탭 하이라이트를 꺼두기 때문에
   (`-webkit-tap-highlight-color: transparent`) 눌러도 아무 표시가 없었습니다.
   옅은 잉크색으로 되살리고, 터치 기기에서는 누르는 동안 살짝 흐려지게 했습니다 (`app/globals.css`).
2. **누른 탭에 밑줄이 차오름** — `useLinkStatus()`로 이동이 진행 중인 동안만 밑줄을 채웁니다
   (`components/nav-links.tsx`).
3. **화면이 바로 바뀌고 뼈대가 먼저 보임** — 섹션마다 `loading.tsx`를 둬서, 데이터를 기다리는 동안
   그 화면 모양의 회색 뼈대가 즉시 뜹니다. Next가 이 뼈대를 미리 받아두므로 탭은 즉시 전환됩니다.
   조각들은 `components/skeleton.tsx`에 모여 있습니다.

`loading.tsx`는 자기 폴더와 그 아래 화면을 모두 덮습니다. 그래서 모양이 크게 다른 화면에는
따로 둡니다 — 달력에서 날짜를 눌렀는데 달력 뼈대가 뜨면 엉뚱하니까요.

```
app/calendar/loading.tsx             달력 그리드
app/closet/loading.tsx               옷장 그리드
app/closet/[id]/loading.tsx          옷 상세·수정
app/closet/new/loading.tsx           옷 등록
app/outfits/loading.tsx              코디 목록
app/outfits/[id]/loading.tsx         코디 상세
```

### 같은 데이터는 한 번만

날짜 화면에 필요한 것 중 **옷 목록과 코디 목록은 어느 날짜를 보든 똑같습니다.** 날짜마다
다시 불러올 이유가 없습니다.

그래서 이 둘은 `app/calendar/layout.tsx`에서 한 번만 불러와 컨텍스트로 내려줍니다
(`components/closet-data.tsx`). 레이아웃은 같은 구역 안에서 화면을 옮겨도 다시 실행되지
않으므로, 날짜를 옮겨 다니는 동안 옷장 조회가 한 번도 일어나지 않습니다.
날짜마다 달라지는 것(그날 기록, 기본 지역, 날씨)만 페이지에서 불러옵니다.

날씨도 마찬가지로 **달력과 같은 범위**로 부릅니다 (`gridRange()`). 하루치만 부르면 날짜마다
새 요청이 되지만, 판 전체를 부르면 달력에서 이미 받아둔 응답을 그대로 씁니다.

### 화면 위로 못 올라가던 것

`globals.css`에 `scroll-behavior: smooth`가 걸려 있습니다. **Next 16부터는** 화면을 옮길 때
이걸 대신 꺼주지 않아서, 부드럽게 올라가다 중간에 멈췄습니다 (PWA에서 특히 눈에 띕니다).
`app/layout.tsx`의 `<html>`에 `data-scroll-behavior="smooth"`를 달아 Next가 예전처럼
이동하는 동안만 꺼주게 했습니다.

### 옷장 거르기는 화면에서

옷은 한 번에 다 받아두고, 전체 → 아우터 같은 거르기는 화면에서 합니다
(`components/closet-browser.tsx`). 칩을 누를 때마다 서버를 다녀오면 느립니다.
고른 조건은 `history.pushState`로 주소에 담으므로 새로고침하거나 링크를 복사해도 그대로입니다.

### 이동 캐시

화면을 옮길 때마다 서버에서 다시 받아오면 느립니다. Next의 클라이언트 라우터 캐시는
`dynamic` 기본값이 **0초**라 (`next.config.ts`의 `experimental.staleTimes`) 매번 다시 받아왔습니다.
60초로 두어, 잠깐 사이에 왔다 갔다 하는 이동은 서버를 부르지 않습니다.

대신 **저장한 내용은 곧바로 보여야** 하므로, 옷·코디·기록을 바꾸는 서버 액션은
`revalidatePath("/", "layout")`으로 캐시를 통째로 비웁니다. 옷 하나가 홈·옷장·코디 만들기·
캘린더에 걸쳐 나오기 때문에, 경로를 하나씩 적으면 빠뜨리는 곳이 생깁니다.
앱으로 돌아올 때도 새로 받습니다 (`components/app-refresh.tsx`).

### 프리페치는 누르려 할 때만

`<Link>`는 기본값(`auto`)이 **화면에 보이는 링크를 전부 미리 받아옵니다.** 달력은 한 판이 40칸이
넘어서, 달력을 열 때마다 날짜 수만큼 서버를 부르게 됩니다. 그렇다고 꺼버리면 누른 뒤에야 받기
시작해 빈 화면을 보게 됩니다.

그래서 카드·칸처럼 여러 개가 늘어선 링크는 **손이 닿거나 마우스가 올라온 하나만** 미리
받아옵니다 (`components/warm-link.tsx`). 터치는 `touchstart`가 `click`보다 100~300ms 먼저
오므로 그 사이에 받아둡니다.

| | 기본 `auto` | `prefetch={false}` | WarmLink |
|---|---|---|---|
| 달력 열 때 | 40건 | 0건 | 0건 |
| 누를 때 | 0건 (이미 받음) | 그때 받음 | 이미 받아둠 |

네비게이션 링크처럼 수가 적고 자주 쓰는 곳은 기본값 그대로 둡니다.

```
items         id, user_id, name, brand, category, subcategory, color_name, color_hex,
              size_label, photo_path, photo_paths(text[]), measurements(jsonb),
              notes, created_at
outfits       id, user_id, name, memo, rating, created_at

               -- (user_id, on_date) 기본키. 지난 날씨를 받아서 넣어둔다
```

카테고리는 `hat / outer / top / bottom / shoes / acc` 6종이고,
카테고리마다 입력받는 실측 항목이 다릅니다 (`lib/categories.ts`).

### 세분류

카테고리 안에서 한 단계 더 나눕니다 — 상의의 `반팔 티셔츠 / 민소매 / 후드티`,
신발의 `운동화 / 스니커즈 / 슬리퍼 / 쪼리` 같은 것들입니다.

- **고르지 않아도 됩니다.** 고른 걸 다시 누르면 풀립니다.
- 목록은 `lib/categories.ts`의 `kinds`에 있습니다. 여기만 고치면 등록 폼이 따라옵니다.
- 카테고리를 바꾸면 세분류 선택은 지워집니다 (상의 세분류가 신발에 남으면 안 되니까요).
  서버에서도 그 카테고리 목록에 있는 값만 받습니다.
- 옷장 검색이 이름·브랜드와 함께 세분류도 찾습니다. "쪼리"로 검색하면 나옵니다.
- 옷장에서 카테고리를 고르면 **그 안에 실제로 있는 세분류만** 칩으로 나옵니다.

- 상의·아우터: 어깨, 가슴, 총장, 소매 (어깨선), 소매 (겨드랑이)
- 하의: 허리, 엉덩이, 허벅지, 밑위, 총장, 밑단
- 모자: 머리둘레, 챙 길이, 높이
- 신발: 사이즈(mm), 발볼
- 액세서리: 길이, 너비

**소매는 두 칸입니다.** 어깨 끝에서 잰 길이와 겨드랑이에서 잰 길이는 다른 값이고,
브랜드 실측표도 보통 둘 다 줍니다. 하나만 적어 두면 나중에 다른 옷과 견줄 때
어느 쪽으로 잰 것인지 알 수 없습니다. 헷갈리는 칸에는 `hint`를 달 수 있고
(`MeasurementField`), 등록 폼이 라벨 밑에 한 줄로 보여줍니다.

`measurements`는 `jsonb`라 항목을 더해도 **마이그레이션이 필요 없습니다.**
`lib/categories.ts`만 고치면 등록 폼·상세·카드가 모두 따라옵니다.
예전에 적어 둔 값은 키가 그대로라 그대로 남습니다.

항목을 늘리려면 `lib/categories.ts`의 `CATEGORY_META`만 고치면 폼·상세·카드가 함께 따라옵니다.
(값은 `jsonb`라 마이그레이션이 필요 없습니다.)

## 사진 업로드

한 옷에 **최대 8장**까지 올립니다 (`components/photo-list-input.tsx`).
**첫 장이 대표 사진**이고 목록·카드·달력에는 그것만 보입니다. `대표로`를 눌러 순서를 바꿉니다.
상세 화면에서는 옆으로 밀어 넘겨 봅니다 (`components/photo-carousel.tsx`).

DB에는 전체 목록을 `photo_paths`에, 대표 한 장을 `photo_path`에 함께 담습니다. 목록 화면이
대표 사진만 보면 되기 때문이고, 예전에 한 장만 올린 옷도 그대로 읽힙니다 (`lib/photos.ts`).

파일은 서버 액션 본문 대신 **브라우저에서 Supabase Storage로 직접** 올립니다. 업로드 전에 캔버스로 긴 변 1600px / JPEG 85%로 압축하고,
경로는 `clothes/<user_id>/<uuid>.jpg` 형태라 Storage 정책으로 본인 폴더만 쓰게 막혀 있습니다.
